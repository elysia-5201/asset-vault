## 3. 清理/生命周期：现状

- **deployed v0.7.1（schema 8）没有清理代码**：全仓无 staging prune/sweep；`stageUnityPackage` 只 `writeFileSync`。
- 工作树**未提交的 v9** 已加 `staging_files` 台账（path_norm/size/plan_id/run_id/job_id/state/created_at/last_used_at/cleanup_error/attempts）与 Repo 方法（`registerStagingFile` / `listStaleStagingFiles` / `deleteStagingFile`），但 **没有调用方、没有 sweep job**（grep 仅定义处）。
- 生产 DB（只读查询）：schema **v8**，**无 staging_files 表**；import_plans 8 条（ready/needs_confirmation），import_runs **0** 条 → 当前 staging 文件不是本轮 0.7.x 计划执行产生，来源更早（10-05 起）。
- 这些目录对应的 assetId（1,6,7,8,9,11,15,16,23,26,27,28,30）在当前库中仍存在（zip/7z 容器），但**没有台账能证明文件仍对应当前内容/版本**；旧导入、资产重建、包更新后都可能成为孤儿。

## 4. 风险

1. **无界增长**：单次导入 190 MB / 485 MB 已出现；无总量上限、无年龄上限。
2. **陈旧复用**：固定 `<assetId>/<label>` 路径，资产内容变化后仍可能读到旧 staging 文件。
3. **崩溃残留**：job 中断/进程退出后目录保留，无启动清扫。
4. **备份盲区**：`win-backup.ps1` 只备份 DB；`win-deploy.cmd` 排除 `data`——staging 不在备份/发布范围（派生数据，但不可恢复）。
5. **审计缺失**：无法回答“这个 staging 文件属于哪次 plan/run、是否还会被用”。
