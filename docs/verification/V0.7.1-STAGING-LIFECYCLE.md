## 2. v9 生命周期实现（已部署）

- schema **v9** 已建 `staging_files` 台账；生产只读查询：**staging_files 0 行**（表存在）。
- 写入：`stageUnitPackage`（structure，`unit-*` 临时目录）与 `stageUnityPackage`（unity.ts，`<assetId>/<label>`）仍只写文件；v9 在导入执行/列表路径登记台账。
- 清理：
  - `cleanupStagingForRun`：run 终态 `verified/partial_success` 立即清理该 run 的登记文件；失败/unknown 保留。
  - `sweepStaging`（`structure.ts:832`）：删除 `last_used_at < now-7d` 且非活跃 run 的**已登记**行；安全边界=路径必须在 unity-staging 内、拒符号链接、dry-run 可用、只删登记行。
  - 启动：`sweepStagingOnStartup`（`server.ts:100`，7 天）。
  - API：`GET /api/staging`、`POST /api/staging/cleanup`（dryRun）。

## 3. 关键事实：历史 793.6 MB 不被清扫

- 生产 `staging_files` **0 行**，而磁盘有 **23 个文件 / 793.6 MB** → 这些是 v9 之前的**未登记历史文件**。
- `sweepStaging` 只处理 `repo.listStaleStagingFiles()` 返回的登记行（`staging_files`），**不会收养/删除未登记文件**。
- 因此：**升级到 v0.7.2 后，这 793.6 MB 仍会原样保留**，需要一次性的“收养/人工清理”策略；新导入才会受 v9 生命周期管理。

## 4. 风险

1. 历史 staging 无台账，无法判断归属/是否过期；不会自动清。
2. 写入端同名覆盖（`<assetId>/<label>`）仍存在；v9 台账可缓解但不改路径语义。
3. 列表抽屉/资产详情仍会往 data/unity-staging 写（`routes.ts:544/1152`），可能产生新的未关联文件（取决于是否登记）。
4. 备份盲区：`win-backup.ps1` 只备份 DB；`win-deploy` 排除 `data`。

## 5. 建议

- 一次性“收养”历史 staging：扫描 `unity-staging` 普通文件 → 以 `stale` 状态登记（记录 size/mtime），再由 sweep 按 7 天/人工确认清理；或显式提供“清空历史 staging”操作（dry-run 先展示）。
- 确认 `routes.ts` 列表/详情 staging 也登记台账并绑定 `plan/run`，避免产生新的未登记文件。
- UI 增加存储占用与清理入口（`/api/staging` 已具备）。
