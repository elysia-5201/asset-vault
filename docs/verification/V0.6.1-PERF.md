# AssetVault v0.6.1-F 小文件吞吐成本归因（verifier / task-12）

- 基线：`main @ cb726e3`（本次只读测量；**未修改 apps/ 与 packages/**，未 git commit/push）
- 时间：2026-10-20 21:10–21:30 (UTC+8)
- 机器：Linux x64，Node 22（`process.version` 见原始 JSON），`cpus()` 见 JSON；同一时刻只跑一个重负载。
- 夹具：临时目录生成 N 个 **内容相同** 的小 zip（每个含 readme.txt + preview.png）；N=500 / 1000，冷缓存（每次运行新建临时库/缓存目录）。
- 插桩：`scripts/bench-costs.mjs`（新增）；端到端对照用既有 `scripts/bench-pipeline.mjs --legacy`。
- 原始数据：`logs/bench-pipeline-{500,1000}{,-legacy}.log`、`logs/bench-costs-*.json`，副本归档在 `docs/verification/evidence/v061-perf/`。

> ⚠️ **夹具缺陷（先读这条）**：`bench-pipeline.mjs` 的 preview.png 是「1×1 PNG + 20KB 补零」。`probeImage` 能读元数据，但 `makeThumbnail` 会 **libpng read error**，而 `media.saveImage` 用 `catch { thumbPath=null }` 静默吞掉（media.ts:33-38）。所以历史/本报告的 padded 运行里，**缩略图编码从未真正发生**，thumbs 阶段偏轻。本报告用 `--valid`（64×64 真 PNG，~16KB）补测真实编码成本，两套数据都列。

## 0. 结论摘要

1. **小文件吞吐：新流水线比 0.5.1 串行路径慢 44–46%。** 500 文件 5.65s vs 3.91s，1000 文件 10.61s vs 7.26s（`bench-pipeline`，同夹具同限制）。差距 ≈ **3.3–3.5ms/资产**，几乎全部来自「每资产 6 个子任务 × 固定调度/DB 成本」。
2. **单任务固定成本 0.42–0.66ms，占 1.7–2.0ms/任务 的 21–33%；两种最大头可被安全消除：**
   - **广播唤醒导致的空轮询**：每个完成任务平均触发 **5.0–5.3 次空 claim**，占索引墙钟 **16%（500）/ 24%（1000）**；
   - **每条语句都重新 prepare**：500 文件 37,152 次 prepare（**756ms，15%**），1000 文件 74,305 次（**1,487ms，13%**）。
3. SQLite 执行成本 0.59–0.84ms/任务；每资产 **147 条语句**（含 6×claim/finish/refresh/enqueue）。
4. 缓存只覆盖 archive 清单：第二轮命中率 ~85–99%，但耗时仍是首轮的 **82–108%**——hash/thumbs/meta/categorize/fts 全部重跑（**重复入队没有"阶段已完成"短路**）。
5. 事件循环稳态 p95 4–7ms；max 348–984ms 是 **一次性模块/原生库预热**（archive 首次加载 348–666ms、sharp 首次 173–403ms），不是稳态瓶颈。峰值 RSS 286–447MB。

## 1. 方法（口径固定，避免退化指标）

| 指标 | 定义 |
|---|---|
| 发现 | `walkCandidates` 枚举 + stat 的墙钟；files/s = 文件数 / 秒 |
| 建档 | `createItem + registerAssets` 墙钟；assets/s；语句数/资产 |
| 每任务 | 索引墙钟 / 完成任务数（一个 zip 资产 = **6 个任务**：hash, archive, thumbs, meta, categorize, fts） |
| 固定调度 | 分别插桩 `claimIndexTask`（含空轮询）、`getAsset`、`refreshAssetState`、`enqueueIndexTask` 的**同步耗时总和** |
| DB 语句 | 在 `db.prepare` 返回的 Statement 上包 Proxy，统计 run/get/all 的**次数与执行耗时**，按 "VERB 表" 分桶；prepare 编译耗时单列 |
| 缓存快路径 | 直接对 `cacheKey/get/put/touch` 做 N 次微基准 |
| 事件循环 | 50ms 定时器实际间隔−50 的 p95/max；按"当时 execute 的阶段"归因（prototype 插桩） |
| 峰值 RSS | 100ms 采样 |

- 插桩有少量额外开销（Proxy + `performance.now`），**绝对吞吐以未插桩的 bench-pipeline 为准**；归因用 bench-costs 的相对值。
- 所有 `avgMs`（stage）是**并发下每任务墙钟**，包含 DB finish/进度 flush 与事件循环争用，不是纯 CPU 时间；ΣstageMs / 墙钟 = 并行度（3.5–3.8）。

## 3. 固定调度成本拆解（bench-costs）

### 3.1 每任务（500 / 1000，padded；括号内为 valid 图）

| 动作 | 500：调用数 | 500：耗时 | 1000：调用数 | 1000：耗时 | 每次 |
|---|---|---|---|---|---|
| claimIndexTask（含空轮询） | 17,952（18,670） | **1001ms**（1062） | 35,808（37,560） | **3204ms**（3398） | 56–89µs |
| ├ 其中空轮询 | **14,952**（15,670） | **834ms**（872） | **29,808**（31,560） | **2670ms**（2855） | — |
| getAsset | 4,000 | 32ms | 8,000 | 60ms | 8–11µs |
| refreshAssetState | 3,000 | 234ms（260） | 6,000 | 500ms（491） | 78–86µs |
| enqueueIndexTask | 3,000 | 224ms（234） | 6,000 | 416ms（412） | 69–75µs |
| **固定动作小计/任务** | — | **422µs**（∪450） | — | **627µs**（∪657） | — |
| DB 执行（全部语句）/任务 | 24.5 条 | 590µs | 24.5 条 | 800µs | — |
| prepare 编译/任务 | 12.4 次 | 252µs | 12.4 次 | 248µs | 20µs/次 |
| **页面墙钟/任务** | — | **1714µs** | — | **1869µs** | — |

- **空轮询放大 = 5.0（500）/ 5.0（1000）次/完成任务**；根因：`Pipeline.notify()` 唤醒**全部** sleeper（pipeline.ts:412），而 8 个 worker 分属 7 个阶段；每次任务完成（3,000 次）与 drain 的 25ms 轮询都会广播。实测 `sleepNotify=14,943/29,799`，`sleepTimeout=9` —— 几乎全部等待都是被广播叫醒去空跑一次 claim。
- 随规模增长：500→1000 assets，墙钟 2.18×，**claim 耗时 3.2×**（56→89µs/次），DB/任务 0.59→0.80ms，说明空轮询 + 重 prepare 在更大库上会**超线性**恶化（10k 小文件会明显更差）。
- 每资产固定动作约：**2.5ms（500）/ 3.8ms（1000）**，与相对 legacy 的差距（3.34–3.46ms/资产）量级一致 ⇒ 结论：**差距主要就是这套固定成本**。

### 3.2 阶段（padded 500 / valid 500）

| 阶段 | padded avg | padded Σ | valid avg | valid Σ | 说明 |
|---|---|---|---|---|---|
| hash | 9ms | 4,500ms | 9ms | 4,500ms | 20KB 文件；墙钟含并发争用、finish UPDATE、进度 flush |
| archive | 4–5ms | 2,000–2,500ms | 5ms | 2,500ms | 小 zip 列目录；命中缓存时更低 |

## 4. SQLite 写入 / 事件 / FTS 成本（500 padded）

| 桶 | 次数 | 耗时 |
|---|---|---|
| SELECT index_tasks | 30,142 | **1,039ms** |
| UPDATE index_tasks | 7,698 | 207ms |
| SELECT item_images | 3,500 | 81ms |
| UPDATE assets | 5,000 | 57ms |
| SELECT assets | 5,500 | 53ms |
| INSERT index_tasks | 3,000 | 53ms |
| DELETE items_fts | 1,000 | 50ms |
| SELECT items | 3,000 | 47ms |
| SELECT archive_entries | 3,000 | 45ms |
| INSERT items_fts | 1,000 | 42ms |
| **合计** | **73,485** | **1,770ms** |

- 索引阶段 **3,500 个事务**（243ms）；建档 5,000 条语句/0 事务。
- **prepare 37,152 次 / 756ms（占索引墙钟 14.7%）**；1000 文件 74,305 次 / 1,487ms（13.3%）。Repo 每次调用都 `db.prepare(sql)`，没有语句缓存。
- 事件记录：happy path **不写** `pipeline_events`（0 条）；`index_tasks` 状态写入 = claim 3,000 + finish 3,000 + 进度 flush ~1,500（hash/archive/thumbs 各一次/任务）；FTS 写 = 1,000 DELETE + 1,000 INSERT。`logPipelineEvent` 单次 28µs——只在 stale/limited/cancel/fail 时产生。

## 5. 缓存快路径（micro，500 padded / µs）

| 操作 | µs/次 | 说明 |
|---|---|---|
| cacheKey | 0.83 | JSON+sha256，可忽略 |
| cache.get(hit) | 27–44 | DB 命中 + 读文件 + JSON.parse |
| cache.put(50 entries) | 90–102 | tmp+rename + upsert |
| cache.touch(DB) | 16–23 | 有 30s 节流，摊薄后更低 |
| probeImage(64×64) | 363–491 | sharp 读元数据 |
| makeThumbnail(512,webp) | **2,268–5,240** | 解码+缩放+编码（波动大，机器争用） |
| media.saveImage | 3,230–2,781 | ≈ probe + thumb，**两次解码** |

- 第二轮实际仍耗 **4,544ms（500）/ 10,812ms（1000）**，为首轮 **88%/96%**；缓存只省了 archive 解析（~0.5–1.0s）。
- **弱身份问题**：首轮 archive 任务常先于 hash 完成，`contentIdentity` 退化为 `weak:size:mtime`（stages.ts:58-61）；500 个相同内容文件产生 ~140 个弱键。hash 完成后第二轮才用 sha256 强键。缓存口径正确但**首轮命中率低**，并导致条目膨胀（属 task-10 范畴，此处只列事实）。

## 6. 事件循环与 RSS

- p95：4–7ms（稳态健康）；max：348ms（500 valid）/ 666–984ms（首次 archive）/ 173–403ms（首次 thumbs）。
- 按阶段归因：`archive` 首次调用 348–666ms、`thumbs` 首次 173–403ms —— **一次性动态 import + 原生库初始化**；之后每阶段 max 均 ≤10ms。预热（启动时后台 import + 一次 sharp 探针）可消除首屏长任务，但不改变吞吐。
- 峰值 RSS：286–324MB（500）、373–447MB（1000）；padded/valid 差异不大。

## 7. 可优化性排序（按实测影响）

| # | 优化项 | 测量方法 | 原始数据（500 / 1000） | 影响估算 | 建议改动 | 破坏大包隔离？ | 破坏恢复？ |

## 8. 夹具缺陷与历史可比性（建议修）

- bench-pipeline 的 `preview.png = 1×1 PNG + 20KB 零填充`：`probeImage` OK、`makeThumbnail` **libpng read error**、`media.saveImage` 静默 `thumbPath=null`（media.ts:33-38）。实测：`/tmp/padded.png` thumb FAIL；同尺寸 64×64 真 PNG thumb OK（7,454B webp）。
- 影响：所有 padded 运行（包括我上面的基线）都**没测到真实缩略图编码**；valid 运行显示 thumbs Σ 9.5s→10.5s（500）、21s→23s（1000），索引墙钟 +9%。
- 建议：bench-pipeline 夹具改为「64×64 真 PNG」或增加 `--valid-images`（与 bench-costs 一致）；否则不同版本间的 thumbs 数据不可比。**本报告同时给出两套数字，结论不依赖 thumbs 绝对值。**

## 9. 最小修复方案（待 lead 批准；本轮未改 apps/）

**P1（纯性能、无语义变化，建议本轮做）**
1. `IndexPipeline.notify` 改按阶段唤醒（sleepers Map<Stage>；enqueue 后只唤醒目标阶段；完成时只唤醒同阶段/下游阶段）。
2. Repo 增加 prepared statement 缓存（Map<sql, Statement>，迁移后清空）。
3. `refreshAssetState` 从"每任务"改为"链尾/无活跃任务时"刷新。
4. `enqueueAsset` 的整条链在一个事务内插入；`claimIndexTask` 用 `UPDATE…RETURNING` 省 getIndexTask。
预计：小文件索引 5.1s → **3.8–4.1s**（≈legacy），1000 文件 11.2s → **8.5–9.2s**。

**P2（需要产品口径，建议随后做）**
5. 入队时按 `fingerprint/version_key` 跳过已 done 阶段（`/reindex?force=1` 保底）。
6. thumbs：先查已登记 sha/已存在 thumb，命中不再解码；probe+thumb 合并单次解码。

**P3（卫生）**
7. 修 bench-pipeline 夹具（见 §8）。
8. 启动预热（#9）。

**明确不动的**：per-stage 并发上限、`index_tasks` 状态机/CAS、回收（recover/promote）、大包 exclusive 语义。上述 P1/P2 均不触碰这些不变量（理由见 §7 两列）。
