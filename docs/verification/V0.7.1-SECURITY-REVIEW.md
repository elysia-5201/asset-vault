## 3. 风险

| # | 风险 | 证据 | 级别 |
|---|---|---|---|
| S1 | 本机任意进程可无鉴权调用 `execute_code` 等，等于**编辑器任意 C# 执行** | 握手无凭据成功；tools/list 含 execute_code | **高** |
| S2 | Unity 实例 token 明文出现在命令行 | 进程 cmdline | 中 |
| S3 | WSL 侧也可访问 8080（跨边界） | WSL curl 握手成功 | 中 |
| S4 | `settings.unity_mcp_url` 可指向远程端点，应用会把 C# 代码/路径发过去 | `routes.ts:232` | 中 |
| S5 | MCP 包版本漂移 + 浮动 `#main` | 9.6.8/10.1.2/10.2.0；lock 无 hash | 中 |
| S6 | 若打开 `AllowLanHttpBind`，桥可暴露到局域网（默认关闭） | `HttpEndpointUtility.cs:156` | 低（默认安全） |
| S7 | 单端口/单 pidfile：同一时间只能服务一个工程 | pidfile 8080 | 低 |

## 4. 结论与建议

- 当前默认配置是**仅 loopback + 无 LAN**，边界正确；但**本机同用户/同 WSL 的任何进程**都能驱动 Unity 执行代码——这是信任边界，不是漏洞修补能完全消除的（MCP 设计如此）。
- 建议：导入/执行类操作前 UI 明确二次确认；`unity_mcp_url` 仅允许 127.0.0.1/白名单；不要把 `AllowLanHttpBind` 打开；固定 MCP commit；Moe 工程补装；对 `execute_code` 类工具在应用侧加“仅本应用使用”的审计日志。
