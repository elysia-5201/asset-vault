## 1. 接口契约（验收脚本按此探测；未落地时对应断言 SKIP）

### FIX-1 导入内容风险扫描（P0，F1）——**已部分落地（本计划按现状校准）**

当前实现（工作树 3e93612+，接口以代码为准）：
- `packages/core/src/risk.ts`：`scanPaths(paths, { incomplete?, blockedReason?, maxHits?=200, maxPaths?=50000 })` → `{ state, hits, scanned, truncated, scannerVersion }`；
  - `state`：`clear | warning | blocked | unknown`（`blocked` 只在调用方显式给 `blockedReason` 时产生；`incomplete` 或超预算 → `unknown`，绝不猜 `clear`）；
  - `type`：`code | assembly | native | editor_code | asmdef`（扩展名映射：cs→code；dll→assembly；so/dylib/bundle/a→native；asmdef/asmref→asmdef；Editor 段下的 cs 归 `editor_code`）；
  - `severity`：asmdef=info，其余=warning；`RISK_SCANNER_VERSION=1`。**只按路径判定，不读内容魔数。**
- `apps/server/src/services/structure.ts`：`computePlanRisk`（包内 pathname + 外层 archive_entries；解析失败置 incomplete）、`applyPlanRisk`（写 `risk_json/risk_state`；warning/unknown→`needs_confirmation`，blocked→`blocked` 且仅未确认时）、`precheckImportPlanWithRisk`（扫描器版本/摘要/state 与快照不一致 → 写回新风险并 `RISK_CHANGED` + blocked）。
- 路由：`POST /api/import-plans` 建计划后自动 `applyPlanRisk`；execute 走 `precheckImportPlanWithRisk`。

剩余缺口（2026-10-22 更新）：FIX-1 的 magic/伪装（RISK_SCANNER_VERSION=2，pdf→PK、png→MZ 判 disguised）与显式 riskAck 门禁（blocked→RISK_BLOCKED，warning/unknown→RISK_REQUIRES_ACK，ack 写 risk_ack_at/digest）**已落地并通过验收**（R6a/R6b/R9/R9b/R10a/R10b）；FIX-2 的 cleanupStagingForRun/sweepStaging 与路由、FIX-3 的 verify-build.mjs 也已落地（G5–G13/B4 PASS）。仍无法自动化：真实 Unity ImportPackage（X1）与 Windows 生产卷磁盘峰值（X2），见 TEST-REPORT 的 BLOCKED。

### FIX-2 staging 生命周期（P0，F3/F8）

新文件 `apps/server/src/services/staging.ts`：

```ts
export interface CleanupOptions {
  dryRun?: boolean; now?: string; maxAgeMs?: number;   // 默认 24h
  runId?: number; maxFiles?: number; maxBytes?: number; // 上限保护（0=不限）
}
export interface CleanupResult { planned: number; deleted: number; bytes: number; protected: number; errors: { path: string; message: string }[] }
export async function cleanupStaging(repo: Repo, stagingRoot: string, opts?: CleanupOptions): Promise<CleanupResult>;
```

规则：
- 只处理 **台账内**（`staging_files`）且 `path` 在 `stagingRoot` 之下（`isSubPath` 段边界）的路径；越界路径只报 error 不删。
- 活跃保护：`state="in_use"` 且 `last_used_at` 在 `maxAgeMs` 内 → protected；关联 run 仍 `running` → protected。
- `dryRun` 只统计 planned/bytes，不删文件不改台账。
- 删除顺序：文件/目录 → 台账行（`deleteStagingFile`）；删除失败 → `state="cleanup_failed"`、`cleanup_attempts+1`、`cleanup_error`。
- 上限：单次最多 `maxFiles`（默认 500）/累计 `maxBytes`（默认 2GB），超出停止并返回。
- 调用点：① `executeImportPlan` 在 `stageUnitPackage` 成功后 `repo.registerStagingFile({path, size, planId, runId, jobId})`；run 结束/失败把本 run 的台账置 `cleanup_pending`；② server 启动 sweep 一次 `cleanupStaging(repo, join(dataDir,"unity-staging"), {}) `；③ 路由 `POST /api/staging/cleanup {dryRun?}` 返回 CleanupResult。
- 越界/删除失败不计入 deleted；绝不递归删 stagingRoot 之外。

影响面：新增 1 文件；改 `structure.ts`（stage 后登记、run 收尾状态）、`server.ts`（启动 sweep）、`http/routes.ts`（cleanup 路由）。
风险：误删用户文件 → 只删台账 + 段边界校验 + dryRun 可先看；台账缺失的旧 staging 目录不自动删（保守）。

### FIX-3 构建一致性校验（P1，F6）

新脚本 `scripts/verify-build.mjs`：检查 ① `apps/desktop/build/server.mjs` 存在；② 含关键路由标记（`/api/import-plans`、`/api/import-runs`）；③ `apps/desktop/build/schema.sql` 与 `apps/server/src/db/schema.sql` **byte-equal**；④ bundle 内 `SCHEMA_VERSION` 与源码一致；⑤ `package.json version` 出现在 bundle banner；输出 JSON 并 `exit 0/1`。接入 `scripts/acceptance.sh` 与 Windows 验收。影响面：仅新脚本 + 文档；无运行时改动。

### FIX-4 MCP 探测缓存（P2，F5）

`unity.ts`：`unityEditorInfo` 结果缓存（TTL 5s，单飞 Promise），失败也缓存 2s 避免每请求等超时；`unityClientFor` 复用 client。影响面：1 文件；风险：Unity 启动后 5s 内仍判离线（可接受，可 env 覆盖）。

### FIX-5 取消/重试语义（P2，F4/F7）

- `POST /api/jobs/:id/retry` 对 `kind==='import'` 显式 `409 IMPORT_RETRY_FORBIDDEN`（语义显式；import 用"重新建计划"）。
- 取消：`cancelImportRun` 把仍 `importing`/`import_command_completed` 的 run_items 置 `unknown`（已发出不可撤回）或 `cancelled`（未发出），并在 summary 记 `possible_side_effect`。影响面：routes/runner/structure 各一处。

## 4. 风险与回滚

- 风险误报（FIX-1）→ 可 ack + 旧计划 null 视为 ok；上线前先用 acceptance 跑夹具集。
- staging 误删 → 台账 + 段边界 + dryRun + 活跃保护；最坏可恢复（重新导入）。
- 构建校验失败多为"忘记重建" → 提示信息给出一条命令（`node apps/desktop/build.mjs`）。
- v9 迁移只加列/表，旧库可回滚为忽略新列；不删除任何历史数据。
